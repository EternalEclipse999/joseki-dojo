# Joseki Dojo — кандидаты в ловушки и запуск KataGo одной командой

- Дата: 2026-10-13
- Статус: согласовано в обсуждении
- Опирается на: [режим «Ловушки» и JDB](2026-10-12-traps-mode-design.md) (разделы 3, 4.1, 4.2)

## 1. Цель

Довести базу ловушек до рабочего состояния за один запуск на машине с мощной видеокартой:
- проверить KataGo ловушки базы `packages/server/bases/traps.jdb` (как `traps:check`);
- дозаполнить кандидатов `scripts/traps/candidates.jdb` (раздел 4.1, пункт 4 спецификации ловушек): KataGo находит недостающие ответы, прошедшие проверку кандидаты переходят в базу;
- закоммитить результат.

Пользователю остаётся одна команда `npm run traps:gpu` и `git push`.

## 2. Объём

**Входит:** дозаполнение кандидатов (раздел 4), команда `traps:gpu` (раздел 3), отчёт, тесты на поддельном движке.

**Не входит:** хранение в базе уровней, на которых срабатывает ловушка (уровни только в отчёте), подбор ловушек под уровень игрока, добавление KataGo новых верных ответов к ловушкам, которые уже в базе. Формат JDB и приложение не меняются; `traps:check` меняется в одном: верные ответы, которые KataGo не подтверждает, удаляются (4.2 спецификации ловушек).

## 3. Команда `npm run traps:gpu`

```
npm run traps:gpu -- [--visits 8000] [--good-max 1] [--caught-gap 2] [--ranks 20k,15k,10k,5k,3k,1k] [--natural 0.1]
```

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `--visits` | 8000 | визитов на запрос анализа |
| `--good-max` | 1 | лучший верный ответ теряет не больше стольких очков |
| `--caught-gap` | 2 | попадание теряет хотя бы на столько очков больше лучшего верного ответа |
| `--ranks` | `20k,15k,10k,5k,3k,1k` | уровни human-сети, на которых ищутся естественные ходы |
| `--natural` | 0.1 | ход естественен для уровня, если его вероятность у human-сети этого уровня не меньше этой доли |

Шаги:
1. **Предварительная проверка**, до всяких расчётов; при любой ошибке — понятное сообщение, ничего не меняется:
   - есть `config.local.json`, KataGo, конфиг анализа, основная и human-сеть; движок запускается, его версия не ниже минимальной и он отдаёт human-политику (та же проверка, что при старте приложения);
   - репозиторий git: текущая ветка не `main` и HEAD не отсоединён; файлы `traps.jdb` и `candidates.jdb` не изменены относительно последнего коммита (остальные изменения в рабочем дереве не мешают и в коммит не попадают).
2. **Проверка базы** `traps.jdb` — ровно как `traps:check` (раздел 4.2 спецификации ловушек) с параметрами команды.
3. **Дозаполнение кандидатов** (раздел 4).
4. **Запись.** `traps.jdb`: результат проверки плюс принятые кандидаты (раздел 4.4); флаг «проверена KataGo» — как его выставила проверка базы. `candidates.jdb`: только непринятые кандидаты, без изменений. Каждый файл пишется атомарно (временный файл и переименование).
5. **Коммит** обоих файлов (только их) от имени и адреса автора последнего коммита ветки — так коммит идёт с адресом noreply репозитория независимо от настроек git на машине. Сообщение: `feat(traps): verify the base and complete the candidates with KataGo`, в теле — сводка (раздел 5), версия KataGo, имена сетей и параметры. Если файлы не изменились, коммит не делается.
6. Печатает сводку и подсказку `Next: git push`. Вывод команды — на английском, как у `traps:check`.

Ошибки движка — как в `traps:check`: запрос, отклонённый KataGo (`query_error`), оставляет ловушку или кандидата без изменений; запрос, на котором упал движок, повторяется один раз, повторная неудача прерывает весь запуск — ничего не записывается и не коммитится.

## 4. Дозаполнение кандидата

Кандидат — узел-ловушка из `candidates.jdb` с путём до него; у него может не быть ответов, верных ответов, или не быть попаданий. Отвечающая сторона — та, что ходит после ловушки.

### 4.1 Отсев до расчётов
- Ход пути вне зоны 11×11 правого верхнего угла — кандидат пропускается с причиной `not a corner sequence`.
- Путь не является допустимой последовательностью ходов — `illegal position`; ответ из файла недопустим — `illegal answer <ход>`. Такие кандидаты остаются в файле с причиной в отчёте.

### 4.2 Верные ответы
- Лучший ход в зоне и его оценка — запрос с `allowMoves` по допустимым пунктам зоны и `untilDepth: 1`, как в `traps:check`. Потеря ответа — та же величина, что в `traps:check` (оценка лучшего хода в зоне минус оценка после ответа, с точки зрения отвечающего; тэнуки — лучший ход вне зоны).
- Если у кандидата есть верные ответы, используются они.
- Если верных ответов нет, кандидатами в верные ответы становятся до трёх первых ходов этого запроса (по порядку KataGo).
- Верными в обоих случаях остаются только ответы, которые теряют не больше `--good-max`. Верные ответы из файла, которые теряют больше, удаляются и попадают в отчёт; такой ход ещё может стать попаданием (4.3), если он естественен.

### 4.3 Естественные ходы и попадания
- Для каждого уровня из `--ranks` — запрос human-политики в позиции перед ответом: `maxVisits: 1`, `includePolicy: true`, `overrideSettings: { humanSLProfile: 'rank_<уровень>' }`.
- Естественные ходы уровня: допустимые пункты зоны с вероятностью не меньше `--natural`; тэнуки — один «ход» с суммарной вероятностью всех допустимых ходов вне зоны и паса (недопустимые пункты human-политика помечает −1, они не считаются).
- Списки по уровням объединяются; у каждого хода запоминаются уровни, где он естественен.
- Естественные ходы, которые уже являются верными ответами, пропускаются. Для остальных считается потеря (4.2). Попадание — естественный ход, теряющий хотя бы на `--caught-gap` больше лучшего верного ответа. Попадания из файла (у нынешних кандидатов их нет) измеряются так же и остаются попаданиями, только если выдерживают этот разрыв.

### 4.4 Решение
- Кандидат **принимается**, если после отбора 4.2 остался хотя бы один верный ответ и есть хотя бы одно попадание (по построению 4.3 разрыв выдержан). Пороги сравниваются на неокруглённых потерях.
- Принятый кандидат переносится в `traps.jdb` как ловушка: путь (недостающие узлы пути добавляются с категорией «нет»), ответы — верные и попадания с потерями, округлёнными до 0,1. Остальные естественные ходы не записываются. Если путь проходит через существующие узлы базы, они не меняются.
- Непринятый кандидат остаётся в `candidates.jdb` как был; причина — в отчёте: `no good answer within <good-max>`, `best good answer loses <x> > <good-max>`, `no natural losing move`, `not a corner sequence`, `illegal …` или текст отклонённого запроса.

## 5. Отчёт

Печатается в консоль и кратко идёт в тело коммита:
- проверка базы: оставлено, удалено с причинами, не проверено;
- удалённые верные ответы (в базе и у принятых кандидатов): ловушка, ход и его потеря;
- кандидаты: принято, не принято с причинами;
- для каждого принятого: идентификатор (3.3), путь, верные ответы с потерями, попадания с потерями и уровнями, например `R14 6.3 (20k 15k 10k)` — потеря и уровни.

Ни отчёт, ни коммит не ссылаются на словарь-источник.

## 6. Устройство кода

- Измерение потерь (лучший ход в зоне, потеря ответа, тэнуки, повтор при сбое движка) выносится из `traps/check.ts` в общий модуль и используется проверкой базы и дозаполнением; `traps:check` меняется только удалением неподтверждённых верных ответов (4.2 спецификации ловушек).
- `traps/complete.ts` — дозаполнение: на входе база кандидатов, движок и параметры; на выходе принятые ловушки (узлы с путями), непринятые кандидаты и отчёт.
- Перенос принятых ловушек в дерево базы — отдельная функция над `JdbTree`.
- `scripts/traps/gpu.ts` — команда: разбор параметров, предварительная проверка, запуск, запись, коммит через `git` (без оболочки, аргументами).
- `package.json`: скрипт `traps:gpu`.

## 7. Проверка

На поддельном движке, без KataGo:
- естественные ходы: порог `--natural`, объединение по уровням с перечнем уровней, тэнуки как сумма вероятностей вне зоны;
- попадание по порогу `--caught-gap`; естественный ход, совпадающий с верным ответом, не становится попаданием;
- кандидат без ответов получает верные ответы из первых ходов KataGo с отбором по `--good-max`;
- верный ответ, теряющий больше `--good-max`, удаляется у ловушки базы (путь к вложенной ловушке под ним остаётся) и у кандидата, попадает в отчёт и может стать попаданием кандидата;
- отсев: не угловая последовательность, недопустимый путь, отклонённый запрос; повтор и прерывание при сбое движка;
- перенос в дерево: новый путь, путь через существующие узлы, вложенная ловушка;
- команда: отказ предварительной проверки (нет сети, ветка `main`, изменённый файл базы) ничего не меняет; коммит во временном репозитории содержит только два файла и автора последнего коммита; без изменений коммита нет.
