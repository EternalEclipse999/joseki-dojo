# Joseki Dojo — ядро: свободный режим

- Дата: 2026-10-06
- Статус: согласовано в обсуждении, ждёт ревью спецификации
- Объём: часть 1 проекта, первая итерация (свободный режим, пустая доска)

## 1. Цель

Тренажёр дзёсеки, в котором можно разыграть угол целиком против соперника, который играет «как человек заданного ранга» и поэтому ошибается, как люди. После розыгрыша программа показывает, сколько очков потерял каждый ход, какой ход был лучшим и какой веткой нужно было продолжать. Отдельно она оценивает, наказали ли вы ошибки соперника.

Целевой пользователь — игрок 9–5 кю. Значения по умолчанию (ранг бота, пороги ошибок) подобраны под этот уровень, всё настраивается.

## 2. Общий план проекта

Проект делится на четыре части, каждая следующая опирается на предыдущие:

1. **Ядро: игра и разбор.** Эта спецификация. Режимы и окружения добавляются по одному за итерацию.
2. **Объяснения.** LLM пересказывает факты из разбора человеческим языком. Источники фактов: потери, ветки, ownership, лесенки, комментарии из базы дзёсеки. Объяснять «из головы» без фактов модели не разрешается.
3. **База дзёсеки.** Импорт внешних баз (Kogo's Joseki Dictionary и/или OGS). Используется для режима «из списка», для намеренных ловушек со стороны бота, для узнавания ветки и для цитат в объяснениях.
4. **Тренажёр.** Карточки по слабым дзёсеки и ненаказанным ошибкам с интервальным повторением (FSRS), статистика.

Итерации части 1 после этой спецификации:
- режимы старта «Случайно» (бот задаёт начало по human-политике) и «Из списка» (небольшой ручной список);
- окружения «Фусеки», «Лесенка» и «Смешанно»: экран выбора, правило «Лесенка только для дзёсеки с пометкой», в свободном режиме «Лесенка» заменяется на «Фусеки».

## 3. Объём

**Входит:**
- экран выбора режима, на котором активен только режим «Свободно»;
- игра в одном углу против human-like бота на пустой доске;
- автоматическое определение конца дзёсеки с подтверждением;
- разбор: потери, кандидаты, лучшая ветка, ownership, метрика наказания;
- «Переиграть с этого хода»;
- хранение тренировок, анализов и ненаказанных ошибок в SQLite;
- установка KataGo и сетей, конфигурация, проверка при запуске;
- фиксация версий KataGo и сетей в `katago.lock.json` (раздел 6.6);
- экран «Настройки» с путями к KataGo и сетям (раздел 7а).

**Не входит:**
- другие режимы и окружения (см. раздел 2);
- объяснения, база дзёсеки, карточки (части 2–4);
- экспорт в SGF, история тренировок в интерфейсе, мобильная вёрстка;
- отмена хода во время игры (вместо неё есть «Переиграть с этого хода»).

## 4. Термины

- **Угол тренировки**: один из четырёх углов (TL, TR, BL, BR), выбирается на экране выбора.
- **Зона**: квадрат 11×11 пунктов от угла тренировки. В координатах Sabaki (`x` слева направо, `y` сверху вниз, 0..18) для левых углов `x ∈ [0, 10]`, для правых `x ∈ [8, 18]`, для верхних `y ∈ [0, 10]`, для нижних `y ∈ [8, 18]`.
- **Тэнуки**: ход вне зоны. Пас тоже считается тэнуки.
- **Дзёсеки началось**: в зоне есть камни обоих цветов.
- **Потеря хода**: сколько очков потерял сыгравший по сравнению с лучшим ходом (раздел 9.2).
- **Ошибка бота**: ход бота с потерей ≥ порога «ошибка» (по умолчанию 2 очка).
- **Нумерация**: ходы тренировки нумеруются с 0. Позиция `t` — позиция перед ходом `t`, позиция 0 — начальная.

## 5. Архитектура

Монорепозиторий на npm workspaces, TypeScript, Node ≥ 22.

```
packages/
  shared/   типы и правила, используются сервером и интерфейсом
  server/   Node: Fastify (HTTP) + WebSocket
  web/      Vite + Preact, доска на @sabaki/shudan
scripts/
  setup/    установка KataGo и сетей, бенчмарк, генерация конфига
data/       SQLite (не в git)
engines/    скачанный KataGo и сети (не в git)
```

### 5.1 `shared`
- Типы: `Color`, `Vertex` (`[x, y]`), `Move` (вершина, `pass` или `tenuki`), `Corner`, `SessionSettings`, `SessionState`, `PositionAnalysis`, `ReviewData`, протокол сообщений WebSocket.
- Правила: обёртка над `@sabaki/go-board` (захваты, ко, самоубийство, легальность хода).
- Координаты: перевод `Vertex` ↔ GTP (`Q16`; буква `I` пропускается; `gtpRow = 19 − y`) и ↔ индекс в массивах KataGo (row-major от A19: `index = y * 19 + x`, индекс 361 — пас).
- Зона: `inZone(corner, vertex)`, `zoneVertices(corner)`.

### 5.2 `server`
- **`engine`** — единственный владелец процесса `katago analysis`. Пишет JSON-запросы в stdin и сопоставляет ответы по `id`. Поддерживает `terminate` и проверку версии (`query_version`). Наружу отдаёт `analyze(query): Promise<Response>`.
- **`bot`** — выбирает ход бота по human-политике (раздел 8.4). Получает RNG снаружи, чтобы тесты были детерминированными.
- **`session`** — состояние тренировки, валидация ходов, кнопка «Тэнуки», определение конца дзёсеки (раздел 8.5), «Переиграть с этого хода».
- **`review`** — считает потери, кандидатов, сводку и метрику наказания из сохранённых анализов.
- **`store`** — SQLite (`better-sqlite3`) и нумерованные миграции.
- **`settings`** — показывает и меняет пути к KataGo и сетям (раздел 7а); версии сверяются с `katago.lock.json` (раздел 6.6).
- **`api`** — WebSocket для игры, HTTP для здоровья системы и данных разбора. Сервер слушает только `127.0.0.1`.

### 5.3 `web`
Экраны: «KataGo не настроен», «Выбор режима», «Игра», «Разбор», «Настройки». Состояние тренировки хранится на сервере, клиент его отображает и отправляет действия.

### 5.4 Протокол WebSocket
Клиент → сервер: `startSession(settings)`, `playMove(vertex)`, `tenuki()`, `finish()`, `continuePlaying()`, `replayFrom(sessionId, turn)`, `resync(sessionId)`.

Сервер → клиент: `sessionState` (любое изменение тренировки: ходы пользователя и бота, «бот думает», предложение закончить), `analysisProgress(done, total)`, `reviewReady(sessionId)`, `error(code, message)`. Коды ошибок: `bad_request`, `illegal_move`, `outside_zone`, `not_your_turn`, `session_not_found`, `session_finished`, `engine_error`, `internal_error`.

HTTP: `GET /api/health` (`state`: `starting` / `ready` / `failed` и причина), `GET /api/sessions/:id/review` (404, если тренировки нет; 409, если разбор ещё не готов), `GET /api/settings` и `PUT /api/settings` (раздел 7а).

## 6. KataGo

### 6.1 Требования
- KataGo ≥ 1.15 (поддержка human-сети).
- Основная сеть для анализа и human-сеть `b18c384nbt-humanv0.bin.gz`.
- Бэкенд любой (CUDA, TensorRT, OpenCL, Eigen/AVX2): проект не привязан к конкретному железу.

### 6.2 Запуск
```
katago analysis -config <cfg> -model <main> -human-model <human>
```
В конфиге анализа задаётся `reportAnalysisWinratesAs = BLACK`, чтобы все оценки были с точки зрения чёрных. Код сам переводит их на нужную сторону, без неявной смены знака.

Правила `chinese`, коми 7.5.

### 6.3 Запросы
- **Ход бота:** `maxVisits: 1`, `includePolicy: true`, `overrideSettings: { humanSLProfile: "rank_<N>" }`. Из ответа берётся `humanPolicy`: 362 числа, `-1` означает недопустимый ход, последнее число — пас.
- **Анализ позиции:** `maxVisits: V_review`, `includeOwnership: true`, без `humanSLProfile`.
- **Проба «пас»:** позиция плюс пас стороны, которая ходит, `maxVisits: V_end`.
- **Тэнуки за пользователя:** `allowMoves` для цвета пользователя содержит все пустые пункты вне зоны, `untilDepth: 1`, `maxVisits: V_end`.

### 6.4 Установка (`npm run setup`)
1. Если в `config.local.json` уже указан путь к KataGo, команда проверяет его версию (≥ 1.15) и наличие сетей.
2. Иначе спрашивает бэкенд и скачивает в `engines/` сборку KataGo и сети, записанные в `katago.lock.json` (раздел 6.6). Каждый файл сверяется по SHA-256. Вместо основной сети можно указать свою.
3. Задаёт число потоков поиска по типу бэкенда: для CPU логические ядра делятся поровну между двумя потоками анализа, для видеокарты ставится 8 на поток. Затем замеряет скорость настоящим запросом и подбирает `V_review` так, чтобы анализ позиции занимал около 2 секунд на этой машине, а `V_end` берёт вдвое меньше. Значения можно поправить вручную. (`katago benchmark` не используется: его вывод рассчитан на чтение человеком, а не на разбор программой, и подбирает потоки для долгих поисков. Для тонкой настройки его можно запустить вручную.)
4. Записывает `config.local.json` и конфиг анализа KataGo.

### 6.5 Проверить при реализации
Документация KataGo утверждает, что human-сеть влияет на поиск только при заданном `humanSLProfile` и ненулевых параметрах `humanSLRoot…`. Это нужно проверить: проанализировать одну и ту же позицию в процессе без `-human-model` и в процессе с ним, но без профиля в запросе. Если результаты расходятся сильнее шума поиска, нужно запускать два процесса KataGo: один для анализа, другой для бота.

### 6.6 Фиксация версий

- Проверенные версии записаны в `katago.lock.json` в корне репозитория: версия KataGo (сейчас 1.18.1), её сборки для Windows и Linux (CPU AVX2, OpenCL, CUDA 12.8), основная сеть `kata1-b18c384nbt-s9996604416-d4316597426` и human-сеть `b18c384nbt-humanv0`. У каждого файла есть ссылка и SHA-256.
- `npm run setup` качает только эти файлы и сверяет суммы. Файл с другой суммой не принимается, а скрипт объясняет, что делать.
- Обновление версии — отдельный PR: правка `katago.lock.json` и успешный `npm run test:katago` на новой версии.
- Свою KataGo и свои сети можно подключить через `npm run setup` или экран настроек. Если запущенная версия отличается от зафиксированной, приложение работает (если версия не ниже 1.15), но показывает предупреждение, что эта версия не проверялась.

## 7. Экран выбора режима

Поля:
- **Режим:** «Свободно» (активен), «Случайно» и «Из списка» (неактивны, с пометкой «скоро»).
- **Окружение:** «Пусто» (активно), остальные неактивны с пометкой «скоро».
- **Ваш цвет:** чёрные / белые / случайно.
- **Ранг бота:** 20 кю … 9 дан, по умолчанию 7 кю.
- **Угол:** TL / TR / BL / BR / случайно, по умолчанию случайно.

Кнопка «Начать».

## 7а. Экран настроек

Открывается кнопкой «Настройки» вне игры и кнопкой «Открыть настройки» на экране «KataGo не настроен».

- **Движок:** пути к исполняемому файлу KataGo, конфигу анализа, основной сети и human-сети. Сети можно выбрать из списка файлов в `engines/models/`. Браузер не сообщает полный путь к файлу из системного окна выбора, поэтому путь вводится текстом, а сервер его проверяет.
- **Анализ:** `V_review` и `V_end`.
- Экран показывает зафиксированную и запущенную версии KataGo и предупреждение, если они различаются.
- «Сохранить и проверить»: сервер проверяет, что файлы существуют, перезапускает KataGo с новыми путями и выполняет проверки раздела 11. Если всё в порядке, новые значения записываются в `config.local.json` и действуют сразу, без перезапуска сервера. Если нет, сервер возвращает прежние пути и показывает причину.
- Незавершённые запросы к KataGo во время переключения повторяются на новом процессе; если переключение не удалось, они завершаются ошибкой, и её можно повторить кнопкой «Повторить».

## 8. Игра

### 8.1 Доска
Доска 19×19, зона подсвечена. Пользователь может ставить камни только в пустые пункты зоны. Недопустимый ход отклоняется ещё в интерфейсе, сервер проверяет его повторно.

### 8.2 Начало
Первый ход за чёрными. Если пользователь играет белыми, бот делает первый ход в зоне (раздел 8.4, до начала дзёсеки).

### 8.3 Тэнуки пользователя
Кнопка «Тэнуки» ставит камень пользователя на лучший ход основной сети вне зоны (запрос из раздела 6.3). В журнале ходов такой ход помечается `actor = auto-tenuki`.

### 8.4 Ход бота
1. Запрос human-политики для профиля `rank_<ранг бота>`.
2. Политика делится на две части: `p_in` — сумма по допустимым пунктам зоны, `p_out` — по остальным допустимым пунктам и пасу.
3. Если дзёсеки ещё не началось, бот всегда играет в зоне.
4. Иначе с вероятностью `p_out / (p_in + p_out)` бот делает тэнуки и ставит камень в пункт вне зоны с наибольшей human-политикой (пас не выбирается).
5. Иначе выбирается ход в зоне с вероятностью, пропорциональной human-политике, возведённой в степень `1 / temperature`. По умолчанию `temperature = 1`.
6. Если допустимых ходов в зоне нет, бот делает тэнуки.

### 8.5 Конец дзёсеки
Для каждой позиции, начиная с начальной, выполняется запрос A — анализ позиции (раздел 6.3). Он же используется в разборе. Когда дзёсеки началось, после каждого хода дополнительно выполняется запрос B — проба «пас».

Если лучший ход (`order = 0`) и в A, и в B лежит вне зоны или является пасом, интерфейс показывает «Похоже, дзёсеки закончилось» с кнопками «К разбору» и «Играть дальше». После «Играть дальше» предложение не появляется, пока не будут сыграны ещё хотя бы 2 хода.

Кнопка «Закончить» доступна всегда. После 60 ходов в тренировке игра автоматически переходит к разбору.

Запросы A и B идут в фоне и не задерживают ходы бота: бот ходит сразу, а предложение закончить появляется, когда приходят результаты.

## 9. Разбор

### 9.1 Анализ
Анализ каждой позиции уже сохранён после запроса A. При переходе к разбору досчитываются только недостающие позиции, интерфейс получает `analysisProgress`.

### 9.2 Потеря хода
Пусть `lead_B(t)` — `rootInfo.scoreLead` позиции перед ходом `t` с точки зрения чёрных. Для хода `t` игрока `P` со знаком `s(P)` (+1 для чёрных, −1 для белых):

```
loss(t) = max(0, s(P) * (lead_B(t) − lead_B(t + 1)))
```

Отрицательные значения (шум поиска) обрезаются до 0.

Потери кандидатов в позиции `t` считаются внутри одного поиска: `loss(c) = best.scoreLead − c.scoreLead` (в единицах стороны, которая ходит).

### 9.3 Пороги (по умолчанию, настраиваются)
| Потеря | Категория |
|---|---|
| < 0,5 | точно |
| 0,5 – 2 | неточность |
| 2 – 5 | ошибка |
| ≥ 5 | грубая ошибка |

### 9.4 Экран
- **Сводка:** сколько всего очков потерял пользователь; сколько раз и на сколько очков ошибся бот; «наказано k из n»; «удержано X из Y очков».
- **Полоса потерь:** по столбцу на ход, ходы пользователя и бота разного цвета, цвет зависит от категории. Клик переносит доску на этот ход.
- **Доска:** сыгранный ход, до трёх кандидатов (`order` 0–2) с их потерей. Кнопка «Показать ветку» проигрывает `pv` лучшего кандидата по шагам.
- **Переключатель «Чья территория»:** показывает `ownership` выбранной позиции.
- **Кнопка «Переиграть с этого хода».**

### 9.5 Наказание
Для каждой ошибки бота в ходе `t` смотрим ответ пользователя — ход `t + 1`, в том числе тэнуки:

- `returned = min(loss(t + 1), loss(t))`, `kept = loss(t) − returned`;
- «наказано», если `loss(t + 1) < 1,0` (порог настраивается);
- сводка: `k` — число наказанных из `n` ошибок бота; `X = Σ kept`, `Y = Σ loss` по ошибкам бота.

Если тренировка закончилась сразу после ошибки бота и ответа пользователя нет, ошибка в метрике не учитывается.

Каждая ненаказанная ошибка записывается в `missed_punishments`.

### 9.6 Переиграть с этого хода
Создаётся новая тренировка с теми же настройками. В неё переносятся ходы `0..t−1` исходной тренировки, а `parent_session_id` указывает на исходную. Если в этой позиции ход бота, бот ходит сразу.

## 10. Хранение

SQLite-файл `data/joseki-dojo.sqlite`. Миграции лежат в `packages/server/migrations/NNN_name.sql`, применённые версии записываются в таблицу `schema_migrations`.

Таблицы:
- `sessions`: `id`, `created_at`, `finished_at`, `mode`, `environment`, `user_color`, `bot_rank`, `corner`, `status` (`playing` / `finished` / `abandoned`), `parent_session_id`, `initial_moves_json`, `summary_json`.
- `moves`: `session_id`, `turn`, `color`, `move` (GTP или `pass`), `actor` (`user` / `bot` / `auto-tenuki`), `in_zone`.
- `analyses`: `session_id`, `turn`, `kind` (`position` / `pass_probe`), `visits`, `payload_json` (сокращённый ответ KataGo: `rootInfo`, до 5 `moveInfos` с `pv`, `ownership`).
- `missed_punishments`: `session_id`, `turn`, `bot_move`, `bot_loss`, `user_move`, `user_loss`, `best_move`, `best_pv_json`, `created_at`.

Конфиг `config.local.json` (не в git, образец `config.example.json` в репозитории) содержит: путь к KataGo, пути к сетям, путь к конфигу анализа, `V_review`, `V_end`, пороги категорий, порог наказания, `temperature`, ранг бота по умолчанию, порт.

## 11. Обработка сбоев

- **KataGo не готов при запуске** (нет бинарника, версия < 1.15, нет сети или human-сети, процесс не стартует). `/api/health` возвращает причину, интерфейс показывает экран «KataGo не настроен» с этой причиной и командой `npm run setup`. Тихой замены бота нет.
- **KataGo упал во время работы.** `engine` перезапускает процесс (до 3 попыток подряд) и заново отправляет незавершённые запросы. Если не получилось, тренировка остаётся в базе со статусом `playing`, интерфейс показывает ошибку и кнопку «Повторить». Кнопка отправляет `resync`: сервер перезапускает KataGo, если тот отказал, и повторяет потерянную работу (ход бота, анализ позиции или подготовку разбора).
- **Обрыв WebSocket.** Клиент переподключается и отправляет `resync(sessionId)`, сервер возвращает полное `sessionState`.
- **Ответ KataGo с `error`.** Запрос отклоняется с понятным сообщением, текст ошибки KataGo пишется в лог. `warning` только пишется в лог.
- **Недопустимый ход.** Интерфейс его не отправляет. Если он всё же пришёл на сервер, сервер отвечает `error` и состояние не меняется.

## 12. Тестирование

Используется vitest, если не сказано иное.

- **`shared`:** перевод координат во всех направлениях (включая пропуск `I` и пас), `inZone` для четырёх углов и граничных линий, правила (захват, ко, самоубийство).
- **`bot`:** подставная `humanPolicy` и фиксированный seed. Проверяется маска зоны, запрет тэнуки до начала дзёсеки, частота тэнуки ≈ `p_out` на большой выборке, выбор пункта тэнуки, отсутствие ходов в зоне, `temperature`.
- **`session`:** определение конца дзёсеки на заготовленных ответах A/B, правило «ещё 2 хода после „Играть дальше“», предел в 60 ходов, «Переиграть с этого хода».
- **`review`:** потери со знаками для обоих цветов, обрезка отрицательных значений, категории, метрика наказания (включая тэнуки в ответ и ошибку бота последним ходом).
- **`engine`:** поддельный процесс KataGo (скрипт, отвечающий заготовленным JSON), сопоставление по `id`, перезапуск после падения, `error` и `warning`. Интеграционный тест с настоящим KataGo пропускается, если `config.local.json` не настроен.
- **`store`:** миграции на пустой базе и повторный запуск без изменений.
- **Сквозной тест (Playwright):** поддельный движок, начать тренировку, сделать несколько ходов, принять предложение закончить, открыть разбор и увидеть сводку.

## 13. Задел для частей 2–4

- **Объяснения (`server/explain`)** получают на вход `ReviewData` и `analyses`, ядро для этого не меняется. Структура `ReviewData` специально содержит факты (потери, кандидаты, ветки, ownership), а не готовый текст.
- **База дзёсеки (`server/joseki`)** подключается через новые режимы в `session`. Поле `mode` в `sessions` уже есть.
- **Карточки (`server/cards`)** строятся из `missed_punishments`, которые копятся с первой тренировки.
- **Новые окружения** задают начальную позицию через `initial_moves_json`, который уже используется «Переиграть с этого хода».
