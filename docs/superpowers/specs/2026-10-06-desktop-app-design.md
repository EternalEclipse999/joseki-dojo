# Joseki Dojo — настольное приложение и установка в пару кликов

- Дата: 2026-10-06
- Статус: согласовано в обсуждении
- Опирается на: [ядро, свободный режим](2026-10-06-core-free-mode-design.md)

## 1. Цель

Человек, который открывает на компьютере только Word и игры из Steam, должен установить и запустить Joseki Dojo в пару кликов, а потом обновлять его одной кнопкой. Никаких Node.js, git, командной строки и вопросов про бэкенды KataGo.

README переписывается на английском: короткая инструкция для игрока и отдельный раздел для разработчика.

## 2. Объём

**Входит:**
- настольное приложение на Electron для Windows (установщик NSIS) и Linux (AppImage);
- встроенный установщик KataGo: скачивание сборок и сетей из `katago.lock.json`, проверка SHA-256, автоматический выбор CPU или видеокарты (OpenCL) по замеру скорости;
- обновление приложения в один клик через GitHub Releases;
- обновление KataGo в один клик, когда новая версия приложения приносит новый `katago.lock.json`;
- CI на каждый PR и выпуск по тегу: сборка, тесты, черновик релиза;
- README на английском.

**Не входит:**
- macOS (у KataGo нет готовых сборок под Mac на GitHub);
- подпись кода (позже, без переделки сборки);
- перевод интерфейса на английский (интерфейс остаётся русским, README об этом предупреждает);
- автоматический выбор CUDA (только вручную в настройках, как сейчас).

## 3. Пользовательский сценарий

1. На странице Releases игрок скачивает `Joseki-Dojo-Setup-X.Y.Z.exe` (Windows) или `Joseki-Dojo-X.Y.Z.AppImage` (Linux).
2. Запускает установщик. Если Windows показывает «Windows защитила ваш компьютер», нажимает «Подробнее», затем «Выполнить в любом случае». Это бывает только при первой установке: обновления приложение скачивает само, и предупреждение не появляется.
3. Установщик ставит приложение в профиль пользователя без прав администратора, создаёт ярлык в «Пуске» и на рабочем столе и сразу запускает приложение.
4. При первом запуске открывается экран «Нужно скачать движок KataGo» с кнопкой «Установить». Дальше всё идёт само (раздел 5), а затем открывается экран выбора режима.
5. Когда выходит новая версия, вверху окна появляется полоса «Доступна версия X.Y.Z» с кнопкой «Обновить». Клик скачивает обновление, приложение перезапускается уже новым.

## 4. Архитектура

### 4.1 Сервер внутри Electron
- Главный процесс Electron запускает тот же сервер (Fastify + WebSocket), что и `npm start`, в своём процессе, на `127.0.0.1` и свободном порту. Окно приложения открывает `http://127.0.0.1:<порт>`.
- `packages/server/src/main.ts` разделяется на функцию `startServer(options)` и тонкую обёртку для командной строки. В `options` передаются пути к файлу настроек, папке данных, папке движков, lock-файлу и собранному интерфейсу, а также порт (0 — любой свободный).
- Путь к `katago.lock.json` больше не вычисляется от расположения исходников: его передают явно. В приложении lock-файл лежит в ресурсах сборки.
- Приложение запускается в единственном экземпляре: второй запуск выводит на передний план уже открытое окно.
- При выходе сервер и KataGo останавливаются.

### 4.2 Где лежат файлы
- Программа: папка установки (Windows: `%LOCALAPPDATA%\Programs\Joseki Dojo`; Linux: сам AppImage).
- Данные: папка профиля Electron `userData` (Windows: `%APPDATA%\Joseki Dojo`, Linux: `~/.config/Joseki Dojo`):
  - `config.json` — настройки (тот же формат, что `config.local.json`);
  - `data/` — база SQLite и журналы KataGo;
  - `engines/` — скачанные сборки KataGo, сети и `analysis.cfg`.
- Обновление приложения не трогает папку данных: KataGo, настройки и история тренировок сохраняются.
- В режиме разработки (`npm start`, `npm run dev`) всё по-прежнему лежит в репозитории.

### 4.3 Сборка
- Сервер и главный процесс Electron собираются `esbuild` в JavaScript. `better-sqlite3` остаётся внешним модулем, `electron-builder` пересобирает его под версию Electron.
- Интерфейс собирается Vite, как сейчас.
- `electron-builder`: Windows — NSIS, установка на пользователя (без прав администратора), ярлыки, удаление через «Приложения»; Linux — AppImage. Публикация — GitHub Releases этого репозитория.
- Новый пакет `packages/desktop` (главный процесс, preload, конфигурация сборки).

## 5. Встроенный установщик KataGo

### 5.1 Когда показывается
- Если KataGo не установлен (нет файлов из настроек, или настроек нет вообще), вместо экрана «KataGo не настроен» показывается экран установки.
- Если KataGo установлен, но его версия или сети не совпадают с `katago.lock.json`, вверху появляется полоса «Доступна новая проверенная версия KataGo — Обновить движок». Клик запускает тот же установщик. Сравнение идёт по отпечатку lock-файла `setup.lockId` = `<katago.version>/<первые 12 символов SHA-256 основной сети>/<первые 12 символов SHA-256 human-сети>`, который установщик записывает в настройки. Если KataGo настроен вручную (нет `setup.lockId`), полоса не показывается.

### 5.2 Шаги
1. **Скачивание** в `engines/`: CPU-сборка (AVX2), OpenCL-сборка и обе сети для текущей ОС из `katago.lock.json`. У каждого файла проверяется SHA-256. Уже скачанные и проверенные файлы повторно не качаются. У каждого файла свой прогресс.
2. **Распаковка** сборок.
3. **Замер CPU**: запуск KataGo с CPU-сборкой и замер скорости, как в `npm run setup`.
4. **Замер видеокарты**: то же с OpenCL-сборкой. Первый запуск OpenCL настраивается до нескольких минут; на экране — «Настраиваю видеокарту — это может занять несколько минут». Если OpenCL не запустился или упал (нет видеокарты, нет драйверов), шаг считается неудачным, и это не ошибка установки.
5. **Выбор**: берётся сборка с большим числом визитов в секунду. По её скорости считаются `reviewVisits` и `endVisits`, как в `npm run setup`.
6. **Запись** настроек: пути, визиты, `setup.kind` (`cpu` / `gpu`), `setup.lockId` (раздел 5.1). Затем KataGo перезапускается на выбранной сборке (`restartWith`) и проходит обычные проверки готовности.

### 5.3 Состояние и ошибки
- Сервер хранит состояние установщика: `idle`, `downloading`, `extracting`, `benchmarking-cpu`, `benchmarking-gpu`, `finishing`, `done`, `failed` — с прогрессом файлов и текстом ошибки.
- API: `GET /api/install` — состояние; `POST /api/install` — запустить (повторный запуск во время работы игнорируется).
- Экран установки опрашивает состояние раз в секунду.
- При ошибке (нет сети, не совпала сумма, KataGo не запустился даже на CPU) экран показывает понятную причину и кнопку «Попробовать снова». Частично скачанные файлы удаляются, проверенные остаются.
- Логика скачивания, проверки и замера переносится из `scripts/setup` в сервер (`packages/server/src/install/`). `npm run setup` остаётся для разработчиков и использует тот же код.

## 6. Обновление приложения

- Используется `electron-updater` с GitHub Releases этого репозитория. Черновики релизов не видны обновлятору, игроки получают только опубликованные версии.
- Проверка при запуске и затем раз в 6 часов. Автоматически ничего не скачивается.
- Если есть новая версия, интерфейс показывает полосу «Доступна версия X.Y.Z» с кнопкой «Обновить».
- После нажатия: скачивание с процентами, затем перезапуск с установкой (`quitAndInstall`). Сервер и KataGo перед этим останавливаются.
- Ошибка проверки или скачивания показывается в той же полосе с кнопкой «Повторить». На игру она не влияет.
- Связь интерфейса с главным процессом идёт через preload (`window.dojoDesktop`). В браузере (режим разработки) этого объекта нет, и полоса обновления не показывается.
- Linux: AppImage обновляется тем же механизмом.

## 7. Выпуск версий

- Версия приложения — поле `version` в корневом `package.json`.
- `npm version patch` (или `minor` / `major`) меняет версию и создаёт тег `vX.Y.Z`, `git push --follow-tags` отправляет его.
- GitHub Actions по тегу:
  1. тесты, проверка типов и сквозной тест на Ubuntu;
  2. сборка на `windows-latest` и `ubuntu-latest` и загрузка файлов в **черновик** релиза (вместе с `latest.yml` / `latest-linux.yml` для обновлятора);
- Владелец проверяет черновик и нажимает Publish — только после этого игроки видят обновление.
- Отдельный workflow на каждый PR в `main`: тесты, проверка типов, сквозной тест. Его можно сделать обязательной проверкой в защите `main`.

## 9. Проверка

- Модульные тесты: установщик целиком — локальный HTTP-сервер раздаёт тестовые zip-архивы и сети, команда запуска KataGo подменяется поддельным KataGo (на Windows поддельный KataGo — скрипт Node, а не `.exe`, поэтому фабрика команды внедряется); выбор сборки по скорости; падение OpenCL → CPU; ошибки загрузки. Также API установщика и `startServer` с явными путями.
- Сквозной тест (Playwright, в браузере): при отсутствии KataGo открывается экран установки с кнопкой «Установить»; после установки, выполненной тестовым режимом сервера (поддельные загрузки и поддельный KataGo), открывается экран выбора режима.
- Ручная проверка на этой машине: собрать установщик, установить, пройти первый запуск с настоящим KataGo, сыграть тренировку.
- Обновление: после публикации двух версий (v0.1.0, затем v0.1.1) убедиться, что кнопка «Обновить» устанавливает новую версию и данные сохраняются.
